## 1. 推荐方案与实际保护范围

采用所有工具共用的执行前检查：工具提供动作和资源描述，核心提供当前执行模式、阶段与授权约束，策略综合决定 allow / ask / deny，核心连接确认与执行。
首版每次 Bash 调用都经独立模型审查；未来边界明确的文件工具可由确定性规则直接放行。未知权限描述保守走 ask。
不先实现完整 Bash AST、关键词黑名单、永久授权数据库或生产级权限平台。

这里实现的是应用层授权。当前本机 Git Bash 不在 OS 沙箱中，模型判决和路径检查都不能证明任意脚本不会越界。
OS 沙箱属于独立的执行环境能力，不自动成为 M4c 的验收前置条件。

## 2. 当前代码与最小接入位置

- 默认注册表目前只注册 `bash`；`read_file` 有实现和测试，但没有暴露给模型。
- `ToolRegistry.execute` 负责查找工具、Pydantic 参数校验、调用 handler 与结果包装。
- `Agent.run` 负责调用顺序、ToolResult 历史配对、进度事件和统一收尾。
- `safety/policy.py` 目前只校验工作目录和 Bash 路径，`ui/prompts.py` 仍为占位。

保留已有调用链，增加一个通用的执行前接点：

```text
Agent 提交完整 assistant 工具调用
  → 核心绑定当前模式、阶段和授权上下文，注入 before_execute
  → ToolRegistry.execute
      → 工具查找、参数校验并固定实际参数
      → 生成工具动作描述
      → 调用核心传入的异步 before_execute
          → safety.evaluate：结合工具动作、模式约束和用户授权，返回 allow / ask / deny
          → ask 时核心等待 UI 的单次确认
          → 拒绝时返回未执行的 ToolResult
      → 只有检查通过才进入 handler
  → Agent 写入配对结果、显示事件、继续循环
```

Registry 不导入 safety 或 UI，不创建裁判模型，不决定确认方式；它只保证 handler 前会经过调用方提供的接点。
Agent 的正常应用路径始终传入权限接点，不提供“未注入策略就默认允许”的应用行为。
Registry 独立单测可以直接验证工具分发，但这不等于应用路径已获授权。

接点的最小语义是 `await before_execute(action) -> ToolResult | None`：None 表示本次可执行，ToolResult 表示本次不执行。
业务上的三态决定由 safety 返回；核心把最终拒绝转换成观察，Registry 不解释审批规则。
暂不拆出 prepare/execute 两套公开调用，也不增加一层只转发调用的执行器。

## 3. 为后续工具预留的动作描述

`ToolSpec` 增加一个由工具维护者提供的动作描述函数；与 handler 一样不暴露到模型 schema。
函数只分析已校验参数，不执行工具、不联网、不读取文件正文；工作目录等可信配置通过注册时的闭包绑定。

动作描述至少包含：

| 信息 | 示例或约束 |
| --- | --- |
| tool_name | 注册表确定的工具名称 |
| arguments | 校验后、补齐默认值的实际参数快照 |
| effects | read、write、execute、network、external_state，可同时存在多个 |
| resources | 明确知道的文件路径、目录、网络目标或业务对象；不强求首版列全资源种类 |
| resource_analysis | complete / partial，表示资源描述是否完整，不代表已经证明安全 |

核心另加 tool_call_id、绑定执行环境、真实用户输入、本次授权范围和执行模式上下文，构成 PermissionRequest。
模式上下文包含当前模式、执行阶段及该阶段的有效权限约束；这些信息由核心绑定，不能由工具参数或主模型文本决定。
工具描述中的副作用与资源由受信任代码产生，主模型不能通过参数声明自己“只读”“低风险”或“已批准”。
描述函数接收参数副本；审批看到的参数与随后传给 handler 的参数必须一致，接点不能就地修改参数。
可用不可变序列化快照保存规范参数；不因等待审批重新解释、补齐或改写待执行命令。

`bash` 的 effects 包含 execute，资源分析通常只能 partial：cwd 只是起点，无法静态列出脚本全部文件和网络访问。
这会将 Bash 路由到模型审查，而不是给它添加“本地执行所以安全”的标签。

后续增加工具时只需补充自身的参数 schema、handler、动作描述及必要的资源检查；Agent 循环不增加按工具名分支。
没有提供权限描述的新工具默认 ask，不能因注册成功或名称像 read/search 就自动放行。

现有 `read_file` 的相对路径仍按宿主进程 cwd 解释，尚未绑定 Agent 的 workspace_dir。
将它注册给模型前，必须统一权限检查与实际打开文件使用的路径：绑定工作目录、处理解析失败及符号链接目标，不能审核一个路径却读取另一个路径。
搜索工具也需对实际遍历/打开的目标落实范围规则，不能只检查起始目录后任意跟随链接；这些应用层检查仍不等于 OS 文件隔离。

## 4. 策略与裁判分工

`safety.evaluate(request)` 返回 PermissionDecision，最小字段为 decision、reason、source。
decision 是 allow / ask / deny；source 用于区分确定性规则、模型判断和后续人工决定，不要求增加风险分数。

以下工具规则均在当前模式和阶段允许的范围内应用；模式禁止的动作先返回 deny，不进入可由普通确认放行的分支。

| 情况 | 建议首版决定 |
| --- | --- |
| 明确的只读工具，资源检查完整、在授权工作区内且未命中禁止路径 | 规则 allow |
| 明确的文件写工具，命中宿主预先授予的工作区写权限，且不涉及受保护材料 | 规则 allow；没有这项授权则 ask |
| Bash 的任何有效调用 | 经独立裁判，再得到 allow / ask / deny |
| 工作区外资源、新的外部接收方、授权或目标不明确 | ask，或先通过已获准的只读工具补证 |
| 发布、部署、共享远端状态修改、扩大权限等需具体授权的动作 | 没有覆盖该动作的授权就 ask；受宿主要求的人工确认约束 |
| 命中用户或宿主明确禁止的资源/行为 | deny；普通确认不能绕过 |
| 工具缺少权限描述 | ask；新增工具时再补清楚规则 |

“工作区写权限”是宿主在会话/任务入口确定的授权范围，不能由主模型自行生成。
首版范围可以只表达工作目录、是否允许普通项目读写、明确禁止项和已有具体授权，不引入角色/租户权限系统。
硬性拒绝优先；模型只在交给它的范围内判断，不能扩大已绑定的执行权限，也不能取消必须人工确认的要求。

不要用 `command.startswith("git")` 等宽前缀直接放行 Bash。
裁判可以允许明确属于任务的普通读取、修改和测试；对 `python task.py` 这类关键副作用无法确定的调用，应 ask 或补证，不能仅凭程序名认可。
检查已有具体授权，避免对同一个已明确批准、且动作未变的请求重复询问；第一版不保存 always 前缀授权。

### 执行模式、阶段与授权共同决定权限

权限请求应回答“这个动作在当前模式和阶段下是否允许”。同一工具、同一组参数，在不同模式下可以有不同决定。
工具只描述动作；模式提供执行约束；safety 统一作出权限决定，工具实现和 Agent 循环不散落 `if mode == ...` 的判定。

需要分别表达两件事：

- 决策流程：例如 ReAct、先规划后执行，决定如何产生下一步动作。
- 执行约束：例如当前只允许读取、允许已授权的项目修改、哪些操作必须确认，决定动作能否执行。

产品中的 plan、auto 可以选择默认流程和约束组合，底层仍分别传递，避免以后把“先规划后执行”写死为“永远只读”，或把 auto 写成“全部放行”。
`modes/` 的实际接口仍按 PLAN.md 留到 M6 从第二种实现中提炼；本节只约定权限输入需要容纳模式与阶段，不提前实现 AgentMode。

参考 Pi 笔记中的模式、审批和沙箱分层，权限上下文还应分别表达以下信息，避免把所有权限隐含在一个模式名称里：

| 维度 | 回答的问题 | 对权限决定的作用 |
| --- | --- | --- |
| 模式与阶段 | 正在调查、等待计划确认，还是执行任务？ | 提供当前阶段的动作约束 |
| 审批策略与交互能力 | 哪些动作需确认，当前入口能否取得人工确认？ | 决定确认要求及其可用性；不能扩大资源授权 |
| 资源授权 | 哪些目录可读、哪些可写，哪些网络目标或远端操作已获准？ | 文件读取、文件修改和网络访问分别检查 |
| 执行环境 | 实际使用本地进程，还是经过验证的受限执行后端？ | 提供真实执行条件；不能用模式名称代替隔离能力 |

模式选择可以给这些维度提供默认值，最终仍受用户和宿主授权约束。auto 不自动开放网络，plan 的只读约束也不自动授予上传文件的权限。
已有审批策略要求人工确认时，独立裁判不能替代确认；审查本身应在 evaluate 内完成，最终 ask 保持“需要人工决定”的语义。
首版只传入实际存在的配置与授权；独立的网络配置、沙箱切换和多种审批配置不自动成为 M4c 的实现范围。

建议的默认语义如下，具体模式名称和切换交互在对应阶段确定：

| 模式或阶段 | 权限约束示例 |
| --- | --- |
| plan：仅调查和制定计划 | 允许授权范围内的只读调查；项目修改和外部状态修改 deny |
| plan-execute：计划待确认 | 保持调查约束；尚未确认时不进入执行阶段 |
| plan-execute：计划确认后的执行阶段 | 按计划和用户实际授予的范围逐次检查动作；计划确认不豁免工具权限检查 |
| auto：自动推进任务 | 在用户授予的范围内自动执行；宿主禁止项仍 deny，需要额外授权的操作仍 ask |

上表是本项目建议的默认语义，不假设其他项目中同名模式具有相同权限。
以后若允许 plan 写入指定的计划产物，应在模式约束中明确该路径和动作的例外授权，不能由 plan 名称隐含授予所有 Markdown 或任意项目文件的写权限。

模式的效果应按动作语义落实：plan 下的写入约束同时覆盖 write_file、Bash 写文件和未来的其他修改工具。
Bash 的 execute / partial 描述不能直接当作只读；仍需审查实际命令是否符合当前只读约束，无法确定时不执行，也不能仅因用户点了普通批准就越过模式禁止项。
这些仍是应用层判定，遵循 §1 的保护范围，不构成脚本副作用的 OS 隔离保证。

建议按以下顺序决策：

1. 应用宿主和用户的明确禁止项，以及当前模式/阶段的硬性约束，命中则 deny。
2. 在剩余范围内应用具体授权、工具资源规则和必要的模型审查；强制确认要求不能被模型取消。
3. 权限不足且允许申请授权时返回 ask；已有授权且符合约束时返回 allow。
4. 核心处理 ask 的确认能力与用户输入；非交互入口仍返回确认不可用，不因 auto 自动批准。

切换模式或阶段必须经受信任的核心入口落实；主模型说“现在进入 auto”或调用参数声明模式，均不改变实际约束。
由 plan 进入执行阶段需要已有流程要求的用户确认。批准计划只覆盖明确授予的目标和范围，新增外部接收方、部署等操作仍按本次动作检查。
待审批请求绑定当时的模式、阶段、授权范围及参数快照；等待期间上下文改变时取消旧审批或按新上下文重新检查，旧批准不能直接沿用。
不把旧模式的 allow 结果缓存为其他模式的权限，也不把计划文本当作可执行操作的无限授权。

### 独立模型审查

裁判是一次独立的非流式请求，不是带工具的第二个 Agent 循环，不复用主 Agent 的 History。
输入包含宿主政策、真实用户请求/明确授权、当前模式和阶段的权限约束、实际动作和执行环境；不把主 Agent 的“安全解释”作为授权证据。
首版不整体复制工具输出、文件正文、Settings、环境变量或凭据；如需补证，通过受控只读路径提供必要材料并标明来源。

`llm/` 保持请求与响应解析的轻薄实现；core 创建裁判客户端并将审查调用传给 safety。
模型连接参数由 Settings 配置，首版可复用当前供应商和凭据，另设 reviewer_model 以选择快速模型；不硬编码未验证的模型名称。
独立请求可以使用同一模型标识，隔离的是会话输入、职责和执行权，不要求一定购买另一种模型。

裁判输出只接受结构正确的三态决定和非空理由；temperature 或自报置信度不作为放行保证。
首版每次调用最多一次审查，不因拒绝自动换模型反复申请。主任务仍遵循既有 max_steps，不新增单轮工具调用数量限制。
审查设独立的有限正数墙钟超时和响应长度边界；需要墙钟上限时由 async 超时落实，不能把 LiteLLM 的读取超时当作总耗时上限。

已知 SDK 请求失败、超时、无效判决均不得执行；首版返回 review_unavailable 的未执行观察，不静默降级到 allow。
内部缺陷和 UI 显示失败仍传播并结束会话；CancelledError 沿用原生取消，不包装成普通拒绝。

## 5. UI 确认、结果与取消

核心通过独立异步确认回调请求输入，不通过同步 `on_event` 回传控制决定。
UI 展示工具名称、完整实际动作、工作目录/目标、当前模式/阶段和理由，返回批准或拒绝；核心不依赖 Console 或 input。
只批准该 tool_call_id 对应的实际参数、执行环境及模式/授权上下文；命令、目标、内容或上下文改变后重新检查。
任意脚本或文件仍可能在审批期间被其他程序修改，因此参数绑定不等于文件内容不可变；严格快照执行另作增强。

- 交互会话可以等待确认；空输入和 EOF 都拒绝。
- `-p` 和非终端入口遇到 ask，立即返回确认不可用的未执行观察，不读取 stdin。
- 2026-10-26 用户选择确认中 Ctrl+C 与 EOF 一样拒绝当前操作，调用执行零次，拒绝观察回灌后模型可继续；这替代此前取消整次运行的设计。当前同步实现只在 input 读取期间临时安装默认 SIGINT 处理器，并在 finally 中恢复原处理器；自动化分流与恢复测试通过，真实终端按键待验收。其他运行阶段的 Ctrl+C 仍取消当前运行。
- 确认读取必须真正可中断，恢复提示符前结束当前读取；不能仅取消 `asyncio.to_thread(input)` 的等待，让后台线程继续消费下一次输入。
- 确认输入与现有 REPL SIGINT 处理只保留一个清晰的责任入口，避免 Task.cancel 后同步 input 仍阻塞事件循环。

普通拒绝继续复用现有结果类型，例如：

```json
{
  "status": "error",
  "output": {
    "reason": "permission_denied",
    "execution": "not_started",
    "error": "目标目录不在本次授权范围内"
  },
  "truncated": false
}
```

permission_denied、approval_denied、approval_unavailable、review_unavailable 要有可区分的原因。
核心照常将结果写入对应 tool_call_id 并发送 ToolResultEvent，模型可在剩余轮数内选择其他做法。
不为首版扩展 ToolStatus 或恢复旧终态事件；审批决定和执行结果分别表达，后续可被 M5 轨迹记录。

**取消接线必须调整当前执行标记。** 现代码在进入 Registry 前就设置 current_call_id；加入审查后，仍等裁判/确认的调用不能据此变成 unknown。
当前调用先保持“未启动”，在全部检查完成、即将交给 handler 时才设置 current_call_id；核心传入的接点可在放行返回前更新该标记，之后不再等待其他审批步骤。
审批阶段取消时，既有 finally 将所有尚无结果的本批调用结清为 not_started；已记录观察保持原样。
进入 handler 后取消仍按已有可确认观察/unknown 规则处理，不自动重跑。标记只用于保守记录，不宣称严格的进程启动原子性。

## 6. 具体文件职责

| 位置 | 建议变化 |
| --- | --- |
| `events.py` | 增加最小共享动作、含模式约束的请求和决定数据，不携带 UI、模式实现或客户端对象 |
| `tools/spec.py` | 增加可选动作描述函数；缺省描述为未知，不改模型可见参数 |
| `tools/registry.py` | 参数校验后、handler 前调用通用接点；保持统一结果与异常语义 |
| `tools/builtin/` | Bash 提供 execute 描述；后续文件工具描述实际资源并检查实际访问目标 |
| `safety/permissions.py` | 三态策略、确定性资源规则及模型审查路由；保留 policy.py 的执行环境校验职责 |
| `llm/reviewer.py` | 裁判请求/响应适配，复用 LLMClient.complete_turn，不执行工具 |
| `core/agent.py` | 绑定当前模式/阶段及授权约束，组装权限上下文、注入接点、连接 UI 确认和结果历史，调整执行阶段标记 |
| `ui/prompts.py`、CLI/REPL | 单次可中断确认；单次入口不提供交互确认能力 |
| `config.py` | 裁判模型、审查超时及有限的宿主授权配置；不整体序列化 Settings |

实际实现时先保持函数和小数据类型，不提前设计 PolicyEngine 插件体系、继承层级或多租户规则 DSL。

## 7. 执行环境增强单独安排

当前 `run_bash` 未传 env，子进程默认继承父进程环境。若启动环境含 API Key 等凭据，它们可能被工具读取。
建议另一步明确子进程环境变量允许集合，并验证 Git Bash、Python/uv、临时目录和取消行为；这能减少凭据暴露，但不能阻止访问磁盘上的凭据文件。
后续沙箱以工作区读写、受保护文件、网络出口和凭据暴露为独立配置；外部资源按需开放，不自动解除整个隔离。
工具描述、注册表接点和沙箱需要覆盖一致的应用调用路径；不能只限制 read_file，却宣称 Bash 不能访问同一文件。

Pi 笔记中的 Operations 接口可作为以后接入第二种执行后端的参考：core 选择并注入实际后端，工具复用参数和结果契约，权限策略检查其是否符合执行要求。
权限策略不自行创建进程、切换后端或因用户批准就移除隔离；审批和实际执行必须使用相同的绑定环境。
当前只有本地 Git Bash，不为假设中的后端提前重构 run_bash，待有真实后端再提炼接口。

## 8. 实施顺序与验收样例

以下是采用本草案后的建议实施顺序，不改写当前阶段确认状态：

1. 固定工具动作、执行约束上下文和三态契约，先用 FakeReviewer 和假确认接通统一检查入口。
2. 接独立真实裁判请求，验证结构化结果、超时、错误分类与输入内容。
3. 接交互确认及中断，再用新增假工具验证不需要改 Agent 循环。
4. 在独立靶子验证正常改代码与审批拒绝；展示证据后由用户确认。

M4c 以当前执行方式为默认上下文，用合成的只读/可执行约束验证权限接口的扩展能力。
真实 plan、auto 模式选择、计划确认与阶段切换在对应模式阶段实施和验收，不新增为 M4c 的前置条件。

关键验收：

| 场景 | 外部可观察结果 |
| --- | --- |
| 工具未知/参数非法 | 既有错误观察，裁判和 handler 均零次 |
| Bash 裁判 allow | 审查一次、handler 一次，输入参数一致 |
| 裁判 deny、人工拒绝、非交互 ask | handler 零次，理由及对应 tool_call_id 可见 |
| 裁判 ask、人工批准 | 先确认后执行一次，只批准当前操作 |
| 裁判超时/请求失败/输出非法 | handler 零次，返回可区分的未执行原因 |
| 模型判决试图覆盖宿主 deny/强制确认 | 宿主决定保持有效 |
| 同一写入动作分别处于只读与已授权执行上下文 | 只读上下文 deny；已授权执行上下文再按工具规则决定，handler 不绕过统一入口 |
| plan 中经不同工具尝试修改，包括 Bash | 均受只读约束；裁判 allow 或普通批准不能取消模式禁止项 |
| auto 下操作越出授权范围或命中禁止项 | 分别 ask / deny，不能因 auto 直接执行 |
| 模式允许本地操作，但未授权外部上传或远端修改 | 分别检查网络和远端资源授权，不因 auto 或“只读来源文件”静默放行 |
| 审批等待中模式、阶段或授权范围改变 | 旧批准不启动 handler；重新检查或取消该请求 |
| 主模型参数或正文伪造当前模式/计划批准 | 不改变核心绑定的执行约束 |
| 审查/确认中取消，本批含多个调用 | 当前及剩余调用 not_started，已有观察不变，pending 清空 |
| 工具执行中取消 | 沿用 M4b 的清理、已知结果或 unknown，不重复执行 |
| 确认中取消后继续输入 | 无残留输入读取；下一次输入只由会话入口消费 |
| 新增已知只读/未知权限描述的假工具 | 分别按既定规则 allow/ask；Agent 无工具名特判 |
| UI 或内部回调失败 | 不继续执行工具，不被误包装成模型请求失败 |

自动化使用 FakeReviewer，不依赖真实模型的随机判决；真实裁判另记录误拦截、漏放和实际延迟，不能用自动化接线测试推断识别准确率。

## 9. 参考 Pi 笔记后的取舍

[Pi 研究笔记](../research/pi-agent-research-deepseek.md)中的架构模式与迁移建议作为设计输入；与本次设计有关的执行前 hooks、模式维度和 Bash 分析行为见[原始来源聚焦核查](../research/pi-permissions-primary-check-20261022.md)。
参考实现的行为不直接成为本项目已验证的能力或当前里程碑要求。

| 参考内容 | 本草案的取舍 |
| --- | --- |
| beforeToolCall / 执行前门控 | 采用统一的 before_execute 接点，保持参数校验、策略、确认与 handler 的先后关系；不额外设计扩展插件平台 |
| 多模式、审批、网络与隔离分开 | 采用可分别表达的权限上下文；先支持当前运行方式，后续模式复用统一入口 |
| AST 分类与默认不放行 | 保留为 Bash 分析实现的候选路线；结构分析可提供副作用和资源线索，未知构造不能因此 allow，AST 也不等于证明任意脚本安全 |
| 独立模型审查 | 保留本草案的 Bash 审查选择，并受确定性禁止项、模式约束和强制确认要求限制；笔记的“必须确定性”不作为唯一设计路线 |
| Operations 执行后端替换 | 在实际引入第二个后端时采用依赖注入；选择和连接由 core 负责 |
| 本会话允许某类操作 | 首版仍只做单次确认；后续若增加会话授权，需明确动作、资源、模式和有效期，不能只存宽泛命令前缀 |
| 工具并行、轨迹、压缩与子代理 | 沿用 PLAN.md 的阶段安排；本次不改变顺序执行，也不提前实现 M5–M8 |

笔记 §4.4 的代码是未完成的示意，不能作为可直接执行的安全策略：仅按 git、find、sed 等命令名放行会遗漏参数副作用，路径也需要按真实执行环境解析。
§4.5 的“按 &&、||、;、| 拆分”应理解为按 shell 语法分析复合结构，不能用普通字符串 split 或正则切片替代。
引号、转义、命令替换和 heredoc 会改变这些字符的含义；若以后采用解析器，必须明确支持的语法、参数规则及解析失败时的 ask / deny 行为。
如果某项放行规则依赖解析器，解析器初始化不可用、语法解析失败和分析不完整都不能静默退回危险词黑名单并 allow；分别记录原因，按当前模式决定 ask / deny。
例如含引号的字面量 a|b 不能误判为管道，cat file > target 不能误判为只读；动态构造无法判断是否满足 plan 约束时不得执行。
这些案例可先用于审查假输入与后续解析方案的测试设计，不把完整 AST、依赖安装或“150–200 行即可完成”的估计作为本阶段承诺。

聚焦核查还发现几处应保留的项目取舍：qings 作者 README 的 plan 有特定 Markdown 写入规则，本项目不能只复制模式名；gatekeeper 的解析器初始化失败存在正则回退，不能概括为所有失败都阻断；Pi 扩展支持修改工具输入，本项目仍要求审批与执行参数快照一致。
