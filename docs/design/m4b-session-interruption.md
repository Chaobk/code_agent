# M4b 设计建议：取消一次运行，继续当前会话

日期：2026-10-19。本文依据当前源码和 [Agent 中断机制研究](../research/agent-interruption.md)
提出实现方案，供用户手写；不是已实现或已验收的声明，不修改 [PLAN.md](../../PLAN.md) 的阶段状态。

2026-10-20 进度：用户已完成下述 UI 取消接线，Codex 补充 9 项回归测试，完整回归 304 项通过。真实终端中断与 Bash 清理异常的联动验证仍待完成，完整 M4b 尚未验收；当前状态以 PLAN.md 为准。

## 1. 本步采用的结构

保留现有 `run_session(agent, *, read_input=None, console=None) -> int` 入口和同步输入。
一个会话复用一个 Agent，每条有效输入创建一个独立的 `asyncio.Task` 执行 `Agent.run()`。
同时只允许一个运行，等待它真正结束后才再次读取输入。

```text
CLI：创建一次 Agent，启动会话
  └── run_session：输入、终端中断、等待本次运行、决定是否继续
        └── 本次运行 Task：Agent.run
              ├── 模型流取消：丢弃未提交的本轮助手消息
              └── 工具取消：清理进程 → 补齐观察 → 结束事件 → 传播取消
```

本步将终端中断接线留在 `ui/repl.py`，必要时抽同文件的私有辅助函数。
不新增 SessionManager、公开 cancel API、取消 Token 或新的运行结果模型。
核心的现有 `CancelledError`、`RunFinished` 和历史契约继续复用。

## 2. 用户可见行为

| 当前情况 | 行为 |
|---|---|
| 空白输入 | 跳过，不调用 Agent |
| `/exit` 或 EOF | 返回 0，结束会话 |
| 等待输入时 Ctrl+C | 放弃当前行、换行、重新提示，不调用 Agent |
| 运行时第一次 Ctrl+C | 请求取消当前 Task，等待其清理与结束 |
| 本次取消尚未结束时再次 Ctrl+C | 不再取消同一 Task，继续等待 |
| 正常完成 | 回到提示符，复用 Agent 和历史 |
| 核心已报告的普通失败或 max_steps 耗尽 | 显示一次原因，接受下一次输入 |
| 未被正常处理的异常 | 显示诊断，返回 1，避免盲目继续 |
| 整个会话被外部 Task 取消 | 让当前运行收尾，继续向上传播取消 |

本步不设计双击 Ctrl+C 退出或强退；清理中可增加“正在取消”的提示，但不能提前显示下一次输入提示符。
`-p` 不进入这个会话中断处理范围，保留单次模式行为。

## 3. 最少需要记录什么

这些概念可以用局部变量表达，不要求建立状态类。

| 名称示意 | 用途 | 生命周期 |
|---|---|---|
| `reading_input` | 区分同步输入和异步运行，让输入时的 Ctrl+C 在读取处被捕获 | 会话内 |
| `current_run` | 保存当前 Task；空闲时为 None | 会话内，每次运行替换 |
| `interrupt_requested` | 记录本次用户取消意图；重复按键只发一次取消 | 每次运行重置 |
| `run_started` | 区分 Task 尚未开始和 Agent 已进入执行 | 每次运行重置 |
| `finished_reason` | 记录核心已经正常呈现的 RunFinished，区分预期停止与意外退出 | 每次运行重置 |

另保存事件循环、会话 Task 和原 SIGINT handler，分别用于安排取消、识别外部取消和退出时恢复。
`run_started` 可由一个很薄的内部协程在 `await agent.run(...)` 前设置；它不承接业务编排。

状态含义是：等待输入、运行中、已请求取消且仍在收尾。最后一种由
`interrupt_requested` 为真且 Task 尚未结束表达，不额外维护第二套相同状态。

## 4. 信号只负责把意图送到正确位置

在 `run_session` 进入循环前安装一次 `signal.signal(SIGINT, handler)`，
最外层用 `finally` 恢复原处理器。安装必须在主线程进行；这是终端会话的运行前提。
当前不将同步 input 放进线程，避免把输入等待和线程取消问题一起引入本步。

处理器只做两件事：

1. `reading_input` 为真：抛 `KeyboardInterrupt`，由读取输入处捕获，换行后继续。
2. 有未结束的 `current_run` 且尚未请求取消：先记录取消意图，再通过
   `loop.call_soon_threadsafe(task.cancel)` 安排取消。

安排回调时绑定当时的 Task，不能让延迟回调重新查找并取消下一次运行。
已经请求过取消或 Task 已结束时不再调用 cancel。处理器不杀进程、不等待 Task、不写历史。
这也替代会话范围内 Runner 默认的 SIGINT 分流；仅创建子 Task 本身不够。

## 5. 由等待结果决定下一步

`cancel()` 只表达请求。会话始终等待本次 Task，并在结束后清空引用与本次状态。
正常完成与取消同时发生时，以实际 Task 结果为准，不能只因取消标志为真就打印“已取消”。

建议的处理规则：

| 等待结果 | 会话动作 |
|---|---|
| 正常返回 | 接受实际完成结果，不再次打印返回正文 |
| CancelledError，且会话 Task 自己正在被取消 | 继续抛出，不能转成继续输入 |
| CancelledError，但没有本次用户取消意图 | 继续抛出，避免把未知来源取消当作用户操作 |
| 本次用户取消，Task 尚未进入 Agent | UI 显示一次“本次输入已取消，运行尚未开始”，然后继续 |
| 本次用户取消，核心已发出 cancelled 结束事件 | 继续输入，不重复显示“运行已取消” |
| 已进入 Agent 却没有正常结束标记的取消 | 显示异常诊断，结束会话，不假定历史已经补齐 |
| 普通异常，且本次不是用户取消、核心已发 error/max_steps 结束事件 | 继续输入，不重复打印原因 |
| 其他普通异常，包括取消期间异常收尾 | 显示意外错误并返回 1 |

`finished_reason` 来自一个很薄的事件回调：先交给现有 `EventRenderer` 显示，
成功后记录 RunFinished.reason。这样渲染本身失败不会冒充已正常呈现的结束。
UI 不生成伪造的核心结束事件；Task 启动前的取消由 UI 自己给出提示即可。

这些规则细化了原先 `except Exception: continue` 的适用范围。
现有受控错误路径由核心维护有效历史；UI 不自行清空 pending、补 tool 消息或重建 Agent。
核心是否兑现这个契约，通过核心与会话联动测试验证，不能仅凭结束事件推断任意资源都已释放。

## 6. 核心与工具的边界

主要实现工作在 `repl.py`，但应通过测试核实以下已有路径：

- `core/agent.py`：模型取消不提交未完成助手轮；工具取消保留已有观察，
  为当前未知结果记录 unknown，为未启动调用记录 not_started；补齐后发结束事件并传播取消。
- `tools/builtin/shell.py`：取消时等待进程清理及输出读取收尾，再传播取消。
  psutil 查询仍是后代快照，不保证所有脱离进程都被清理。
- `context/history.py`：只向模型提供配对完整的历史；UI 不绕过检查。
- `tools/registry.py`：普通工具失败仍返回错误观察，模型可以修正；取消不能被普通错误包装抹掉。

需要专门补一个联动案例：Bash 已收到取消，但清理函数又抛普通异常。
当前 shell 清理会抛 RuntimeError，而 Registry 捕获普通 Exception；因此需要验证这条组合路径
不会把用户取消转成普通工具错误后继续执行剩余命令。发现问题时在资源/核心边界修复，
不让 REPL 猜测进程状态，也不在本设计中提前规定新的异常类型。

用户取消不撤销磁盘修改；下一次运行也不自动重跑 unknown 命令。
清理失败必须可见，不能把“历史配对完整”当作“进程已全部终止”的证明。

## 7. 实现和验证顺序

1. 先补失败与耗尽后第二次输入的 FakeLLM 测试，落实普通异常的继续/退出规则。
2. 建立每次运行的 Task、事件观察和状态重置；先用假运行触发取消，不依赖真实信号。
3. 安装并恢复 SIGINT handler，接输入中断和运行中断；测试中捕获注册的 handler，
   调用回调验证分流，不向 pytest 主进程发送真实 SIGINT。
4. 用真实 Agent + 假模型/假工具验证取消后的第二次请求，检查历史、步数与工具执行次数。
5. 在真实终端验证输入中断、模型输出中断和 Bash 中断，随后继续提问；单次模式做回归。

关键断言：同一会话只创建一个 Agent；取消请求只发送一次；清理结束前不读下一条输入；
已执行结果保留、未启动工具执行零次、pending 清空；第二次运行不含失败流的临时助手内容；
错误和取消提示不重复；外部取消传播；所有退出路径恢复旧 handler。
另覆盖 Task 启动前取消、清理异常及结束事件回调异常。

按项目分工，由 Codex 准备规格与关键测试，用户手写逻辑，之后评审与验收。
本文最初仅记录设计；2026-10-20 已完成 UI 接线和上述自动化验证，后续仍需第 6 节的 Bash 清理异常联动与真实终端实验，不宣称完整 M4b 已通过。
