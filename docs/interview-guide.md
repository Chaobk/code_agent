## 一、项目介绍与工具协议

### Q01. 用一分钟介绍你的 Agent 项目。

**参考回答：**这是一个用 Python 手写核心的编程 Agent，用来理解和验证“模型选择行动、应用执行工具、观察回灌、模型再决策”的过程。当前已完成非流式闭环，默认只开放 Bash，让模型读取和修改独立靶子并运行测试。我重点处理了参数校验、工具结果配对、超时与取消、输出预算，以及结束和成功的区别。现在正在做流式组装，记忆和多 Agent 是后续阶段。核心实现由我完成，Codex 协助规格、测试和评审。

**追问：**怎样证明它真的完成任务？答：独立运行固定测试并核对 diff，而不是只看模型说“完成”。展示材料来自 [验收历史](plan-history.md)，不用未测量的成功率或成本提升作结论。

### Q02. Agent、Workflow、普通 LLM 调用有什么区别？ReAct 又是什么？

**参考回答：**普通调用完成一次输入到输出；Workflow 由程序预先规定主要步骤和分支；Agent 让模型根据目标和观察动态选择下一步行动。两者可以结合，例如固定的权限流程包围动态决策循环。ReAct 强调推理与行动、观察的交替，不要求解析某种“Thought:”文本格式。本项目用原生工具调用表达行动，程序负责执行和回灌；不会把模型输出的思考文本当成执行许可或可靠审计证据。

**追问：**是不是任何循环调用 LLM 都是 Agent？答：还要看是否由模型根据环境反馈选择行动；固定重试循环本身不能说明有自主决策。流程稳定、约束明确的任务优先考虑可预测的 Workflow。

### Q03. 为什么不直接用 LangChain / LangGraph？你的模块怎么划分？

**参考回答：**学习目标是看清协议和状态，所以先手写最小实现。LLMClient 只接模型；ToolRegistry 管 schema、参数校验和 handler；History 管消息与配对；Agent 连接它们并决定何时继续；UI 负责展示。这样可以用 FakeLLM 独立验证循环。如果未来需要持久化图状态、复杂分支或人工暂停，我会用同一案例比较框架减少了哪些代码、引入了哪些约束。没有使用框架不代表框架没有价值。

**项目证据：**[Agent](../src/code_agent/core/agent.py)、[模型适配](../src/code_agent/llm/client.py)、[Registry](../src/code_agent/tools/registry.py)。**追问：**为什么不先写通用模式接口？第二种模式尚未落地，当前抽象容易只适配第一种实现。

### Q04. 项目中最值得展开的技术难点是什么？

**参考回答：**我会选择取消时的状态一致性。假设模型一次返回 A、B、C 三个调用，A 已执行，B 执行时取消，C 尚未开始。如果只抛异常，历史会留下没有结果的调用，后续请求也无法判断副作用。我的处理是保留 A 的结果，B 有观察就保存，没有就记 unknown，C 记 not_started；补齐配对后继续传播取消。这维护了可继续的历史，但没有声称撤销 B 已经发生的修改。

**项目证据：**[取消回归测试](../tests/code_agent/core/test_agent.py) 中的 `test_run_pairs_cancelled_batch_and_can_resume` 与 `test_run_preserves_observation_from_cancelled_tool`。这是可讲的技术案例；若描述排障时间线，应补自己的实际经历，不能把示例改写成不存在的事故。

### Q05. Agent 什么时候结束？模型说完成就算成功吗？

**参考回答：**在当前 Chat Completions 契约里，正常 stop 且没有工具调用，表示本次循环结束；同轮有调用时，即使文本声称完成，也先执行并回灌观察。异常 finish_reason、步数耗尽和取消另行处理。工具执行 completed 只表示取得了执行结果，例如 pytest 返回非零仍是一条有效观察。任务是否成功要由固定测试、diff 和用户要求判断，CLI 正常退出也不是测试成功证明。

**追问：**为什么不用 END_TASK 或 finish_task？文本标记不是当前必需条件；结构化结束工具也只能提供可校验的申报字段，不能证明外部任务成功。见 [现有结束分支测试](../tests/code_agent/core/test_agent.py)。

### Q06. Function Calling 的完整流程是什么？

**参考回答：**应用给模型工具名称、描述和参数 schema；模型返回工具调用请求；应用解析并校验参数，检查执行策略，调用工具，再把结果关联到调用 ID 送回模型。模型提出调用，真正执行的是应用。就本项目所用 Chat Completions 格式而言，assistant 消息保存 tool_calls，结果使用 role=tool 和对应 tool_call_id；其他 API 的消息结构应按各自协议适配。

```text
assistant: calls = [id=a, name=bash, arguments=...]
tool:      tool_call_id=a, content=序列化的 ToolResult
assistant: 根据观察继续调用，或无工具的 stop 结束
```

**追问：**模型生成不存在的工具名怎么办？Registry 返回错误观察，不执行任意字符串指定的函数。当前已做参数校验；表述中的权限策略仍属 M3 计划。

### Q07. 有 JSON Schema / 结构化输出，还需要后端校验吗？

**参考回答：**需要。结构约束解决输出形状问题，不能证明路径、账号、资源范围和业务操作被授权，也不能证明命令语义正确。即使供应商支持严格 schema，应用仍要校验参数和业务前提。本项目用 Pydantic 在调用 handler 前校验参数，例如超时范围、空白命令和额外字段；workspace_dir、bash_path 由应用绑定，不接受模型覆盖。具体权限策略还未接入。

**项目证据：**[BashArgs](../src/code_agent/tools/builtin/shell.py)、[参数测试](../tests/code_agent/tools/builtin/test_shell.py)。**追问：**合法的 command 字符串一定安全吗？不一定，字符串类型校验无法替代命令执行边界。

### Q08. 工具报错应该抛异常，还是作为结果返回给模型？

**参考回答：**按错误所在层处理。完整调用的未知工具、参数错误、工具执行异常可以转成结构化观察，让模型修正；Bash 正常启动后的非零退出保留 exit_code，不伪装成基础设施崩溃。模型响应协议异常通常停止本轮，取消应在清理后继续传播。统一 ToolResult 是为了让上层稳定消费，不是把所有失败压成一个字符串或假装成功。

**追问：**JSON 参数写坏了算断流吗？不一定。收到完整正常响应后的非法 JSON 是参数错误；缺结束片、连接中断等才是传输/组装问题。证据见 [Registry](../src/code_agent/tools/registry.py)、[ToolResult](../src/code_agent/events.py)。

### Q09. 为什么专门做 History，直接维护 list 不行吗？

**参考回答：**list 可以存数据，但不会维护协议不变量。我的 History 验证消息角色、同批调用 ID 唯一、结果必须对应 pending 调用；批量校验通过后才改变状态，避免第二个调用坏了却已经写入第一个。有 pending 时可以读取展示历史，但拒绝提供模型历史。输入和返回快照深拷贝，避免外部修改悄悄破坏内部状态。

**追问：**pending 代表工具未执行吗？只代表尚未记录结果，可能已经发生副作用。深拷贝也不等于线程安全或允许同一 History 并发写。证据见 [History](../src/code_agent/context/history.py) 与 [配对/快照测试](../tests/code_agent/context/test_history.py)。

## 二、流式与工具调度

### Q10. 流式工具调用为什么不能收到一点参数就执行？

**参考回答〔组装与循环已实现，终端事件待接线〕：**参数可能跨片，多个调用也可能交错，某一时刻恰好能解析的 JSON 不代表整轮已经正常完成。我已实现按调用 index 缓存 ID、类型、名称和参数增量，流正常耗尽后检查结构并生成完整助手消息；提交历史成功后，再交给 Registry 顺序校验与执行。FakeLLM 测试验证了交错调用的执行顺序，以及断流、缺结束片时本轮执行零次、未提交内容不进入历史。终端实时事件和真实流式靶子尚未验收。index 用于当前轮的片段归属，调用 ID 用于结果配对，两者不能混淆。

**追问：**“执行一次”保证到什么范围？当前设计防止同一组装结果被分片触发多次执行，不承诺跨重试、崩溃或远程系统的 exactly-once。见 [M2b 练习](../src/code_agent/llm/streaming.py) 和 [PLAN](../PLAN.md)。

### Q11. 流式文字已经显示了，随后失败，历史怎么处理？

**参考回答〔进行中〕：**实时展示与完整消息提交是两件事。UI 可以显示 text delta，但 History 只接收通过本轮协议校验的完整消息。断流后提示本轮中断，暂存文字不成为下一次模型请求里的完整 assistant 消息；此前已经提交的工具结果仍保留。完整消息事件也不能让 UI 再打印一遍已显示的正文。

**追问：**需要保留失败时的半截文字诊断吗？可以在诊断轨迹中记录并标记未提交，不能把诊断记录直接当成可恢复对话。验证方法是注入“文字 → 异常”，检查显示、历史和工具执行次数三个结果。

### Q12. 模型一次返回多个调用，为什么不全部并行？

**参考回答：**模型同时给出多个调用不代表它们没有依赖。例如修改文件、运行测试必须有顺序；两个写操作可能覆盖同一文件。当前按顺序执行全部调用，简化副作用和取消语义，也没有单轮调用数量上限。后续只对独立只读调查考虑并行，并显式管理资源冲突、结果归属、失败和取消；不能只把 for 循环替换成 gather。

**追问：**并行结果按哪个顺序回灌？先定义稳定顺序，使用调用 ID 关联，不能依赖完成先后猜对应关系。请求轮数预算也不等于调用次数、耗时或费用的完整上限。

## 三、Python 异步执行与可靠性

### Q13. Bash 输出为什么要同时读 stdout 和 stderr？截断以后为什么继续读？

**参考回答：**两个管道都有有限缓冲，只读一个或先等进程退出，可能因另一个写满而互相等待。当前用两个异步读取任务并发排空；共享 20,000 字符的保留预算，超限后丢弃新增内容但继续读取，避免子进程被管道阻塞。UTF-8 字符可能跨读取块，用增量解码器处理。这个预算限制保留文本，不是 token 数，也不是整个进程的内存上限。

**项目证据：**[collect_output](../src/code_agent/tools/builtin/shell.py)、[并发排空/跨块解码测试](../tests/code_agent/tools/builtin/test_shell.py)。**追问：**为何不直接 communicate？它方便处理双管道，但一次收集全部输出不适合这里的有界保留目标。

### Q14. async/await、to_thread、Task.cancel 分别解决什么？

**参考回答：**async/await 适合模型请求、子进程 I/O 等等待操作，让其他任务获得调度机会；它不自动加速 CPU 密集计算。同步阻塞 handler 可以放到 to_thread，避免阻塞事件循环；普通 CPython 中线程也不是通用的 CPU 并行方案。Task.cancel 请求协程在可取消点处理取消，不会自动杀掉线程里正在执行的函数，也不等于终止子进程。

**追问：**那怎样停止实际工作？协程清理后传播 CancelledError；线程任务需要合作式停止或其他隔离方式；子进程显式终止并回收。当前 Registry 支持同步 handler，但不能据此宣称所有工具都可强制取消。见 [Registry](../src/code_agent/tools/registry.py) 和 [官方核查](research/agent-interview-sources.md)。

### Q15. 超时、取消、进程终止和回滚是同一回事吗？

**参考回答：**不是。超时是超过等待期限，取消是上层要求停止；两者都需要处理实际执行资源。进程终止只是停止后续执行，已写文件不会自动恢复。本项目对 Bash 尽力清理已发现的进程树，超时保留已获取输出并返回 timed_out；取消清理后传播。核心在缺少可确认观察时记录 unknown。psutil 后代快照无法保证发现所有后代，所以不能把它描述为严格进程隔离。

**追问：**能否用 shield 保证工具不会被取消？shield 只影响特定 await 的取消传播，不能代替资源清理，也不意味着任务永远不会被取消。项目用它保护输出收集，使清理期间仍能排空管道，见 [run_bash](../src/code_agent/tools/builtin/shell.py)。

### Q16. Agent 失败为什么不能直接重试？如何考虑幂等？

**参考回答：**要区分模型请求、只读工具与有副作用的命令。网络超时不证明远端未处理，工具没有返回也不证明文件未修改。当前不会自动重跑 unknown 命令。生产设计可对适合的请求做有界重试和退避，对业务操作用执行端幂等键、状态查询或补偿；重试单次操作与重放整条 Agent 链是不同的风险。通用 Bash 很难自动证明幂等，需要先检查目标状态。

**追问：**tool_call_id 能保证 exactly-once 吗？它提供关联，不自动提供跨进程、跨重试的持久去重与原子提交。文件已改但结果未落盘是一个必须承认的崩溃窗口；当前只有取消配对，没有生产级执行账本。

## 四、会话、上下文、记忆与 RAG

### Q17. 会话、一次运行、一轮请求、恢复分别是什么？

**参考回答〔已有 History，完整 REPL/恢复待实现〕：**会话保存多次输入的历史；一次运行由一次用户输入触发，有自己的步数和取消状态；一轮请求是一次模型响应以及相关工具观察。恢复是加载一个可解释的检查点继续工作，回放只是展示旧事件。计划先从配对完整的检查点恢复，记录格式版本和白名单配置，凭据从当前环境加载。恢复对话不等于恢复磁盘，继续前要检查文件是否变化。

**追问：**直接保存 Settings 和 messages 够吗？Settings 含 api_key，不能整体落盘；还要验证格式、历史完整性和运行环境。当前 core 可以保留历史，但 CLI 多轮输入和 --resume 尚未接入，见 [M4/M5 计划](../PLAN.md)。

### Q18. 上下文超长如何处理？为什么不能只截掉前面的 token？

**参考回答〔M6 计划〕：**先决定必须保留的目标、约束与系统指令，再按相关性和时间选择历史、工具输出、记忆和知识片段。工具调用及结果成组处理，避免破坏协议；原始记录保留，裁剪只作用于本次模型输入。还要为模型输出预留空间，预算里包括工具 schema 等请求内容。总结可能遗漏或改写事实，应保留来源；必保留内容都放不下时应明确失败或让用户缩小任务。

**追问：**大上下文窗口是否意味着不用检索？窗口解决能否容纳，不保证相关信息被正确利用，也不消除成本与延迟。验证应同时检查预算、配对和任务结果；当前已有工具输出字符预算，但没有实现 token 级裁剪。

### Q19. RAG、微调、长上下文怎么选？

**参考回答〔M5d 计划/扩展〕：**RAG 在生成前检索外部材料，适合需要更新和可追溯证据的知识；微调改变模型参数，通常用于适配行为、格式或特定任务表现，不能自动保证事实实时更新；长上下文允许一次放更多材料，但仍需选择信息。三者可以组合，不能说做了 RAG 就不能微调。本项目先通过文件和关键词定位代码与文档，验证来源是否支持回答，再按失败案例决定是否需要向量检索。

**追问：**RAG 能消除幻觉吗？不能，召回不到、召回错误、材料过期或生成不遵循证据都可能失败；需要分别评测检索和生成。当前 Bash 按需读源码也不能直接包装成已完成一套 RAG 系统。

### Q20. 一个基本检索链路怎么设计？chunk、向量、重排各有什么用？

**参考回答〔方案题〕：**先解析材料并保留来源，按标题、段落或代码结构分块，再用关键词/向量或混合方式召回候选，按需重排后在预算内注入。关键词适合精确标识符，向量用于语义相近表达，重排进一步判断问题与候选的相关性。块太小可能缺上下文，太大可能带入噪声；重叠会保留边界内容，也会增加重复。块大小、top-k 和重排数量应在自己的问题集上调，而不是背固定数值。

**追问：**换 embedding 模型怎么办？检查向量维度与语义空间兼容性，通常需要重建相应索引并保留版本；不能混用不同空间的向量。代码中的函数名、错误码和路径值得保留精确检索通道。这些是设计建议，当前未实现向量索引。

### Q21. 长期记忆和聊天历史有什么区别？怎样防止记错？

**参考回答〔M5c 计划〕：**聊天历史保存发生过的交互；长期记忆是经过选择、能够跨会话复用的事实或经验。工作记忆关注当前目标和观察，情景记忆记录一次经历，语义记忆保存事实，流程经验表达可复用步骤；分类服务于设计，不必每类建独立数据库。我的计划用文件保存条目，带作用域、来源、更新时间和有效状态，写入前核实，查询时过滤过期条目并保留证据。

**追问：**新事实与旧事实矛盾怎么办？先核查来源和适用范围，更新或作废旧条目；不能仅按模型自信程度覆盖，也不能把未经验证的总结写成事实。项目与用户作用域要区分，跨租户隔离属于后续服务化设计。

### Q22. RAG 回答不好，如何判断是检索问题还是生成问题？

**参考回答〔方案题〕：**准备带相关材料和参考判据的问题集，先看召回结果，再看最终回答。Recall@k 是相关材料中有多少进入前 k 个，Precision@k 是前 k 个中有多少相关；相关性的标注单位要固定。若给定正确材料仍答错，重点查上下文组织和生成；若正确材料没进候选，查解析、分块、查询与召回；候选有但没进入注入范围，则查排序与预算。

**追问：**回答带引用就算有依据吗？还要检查引用片段是否支持具体断言、是否适用和过期。加入无答案问题，检查能否承认缺少证据；同时记录时延和成本，不能只优化一个检索指标。指标与实验方案是面试设计内容，项目尚未产出 RAG 评测结果。

## 五、安全与权限

### Q23. Prompt Injection 是什么？只在 system prompt 里说“不要听文档指令”够吗？

**参考回答〔M3 计划/生产扩展〕：**工具结果、网页或仓库文件可能夹带要求模型改变目标、泄露数据或调用工具的指令。风险在于把低信任的数据当成了控制指令。提示词有帮助，但执行端还应限制工具权限与数据范围，把高影响操作绑定到具体授权，隔离执行环境，并对外发内容和副作用做检查。检索到内容或子 Agent 发来请求，都不自动产生用户授权。

**追问：**怎样测试？构造带伪造指令的仓库说明，检查是否发生越权调用或敏感数据外发；只检查模型口头拒绝不够。当前项目尚未接入完整策略或隔离，不能宣称已经解决提示注入。

### Q24. 固定 cwd、用 create_subprocess_exec，就能安全执行 Bash 吗？

**参考回答：**不能。cwd 是初始工作目录，命令仍能访问绝对路径、上级目录或网络。create_subprocess_exec 不会隐式增加 shell，但本项目显式启动了 `bash -c command`，command 仍由 Bash 解释。学习阶段用独立靶子与可信环境；若服务化，需要按实际威胁模型限制文件系统、网络、凭据和资源，并验证隔离。简单黑名单和只读提示词不是执行级只读保证。

**追问：**专用文件工具有什么好处？输入范围更窄，更便于校验、审计和授权；Bash 的优势是通用和组合能力强，代价是难以完整分析副作用。见 [执行器](../src/code_agent/tools/builtin/shell.py) 与 [M3 范围](../PLAN.md)。

## 六、评测、诊断与性能

### Q25. 模型不稳定，Agent 怎么做自动测试和评测？

**参考回答：**分三层。工具单测验证参数、执行和清理；FakeLLM 返回固定响应序列，验证配对、异常结束和取消等确定性控制逻辑；真实模型在独立靶子上完成任务，再用固定测试和 diff 检查结果。固定模型、配置和初始状态，重复运行记录实际成功次数与总次数。不能把 FakeLLM 测试通过当成模型能力，也不能用一次成功宣称稳定；temperature=0 也不是全链路可重复性的保证。

**项目证据：**[核心测试](../tests/code_agent/core/test_agent.py)、[Bash 测试](../tests/code_agent/tools/builtin/test_shell.py)、[验收记录](plan-history.md)。**追问：**如何防止“改测试让它绿”？保留固定测试并独立检查 diff；更严格评测可用 Agent 不能修改的验证材料。当前真实验收仍手动，M7 才自动化任务集。

### Q26. Agent 失败时，你怎么定位？该记录什么？

**参考回答：**按链路分层：目标是否理解正确，模型请求/响应是否有效，工具名和参数是否正确，执行环境是否失败，观察是否完整回灌，最后判据是否达标。先找第一次偏离预期的步骤，避免只看最终答案。计划轨迹关联 session、run、step、tool_call，记录配置摘要、耗时、停止原因、工具状态、exit_code 和截断信息；日志字段应满足诊断需要并控制敏感内容。

**追问：**为什么不记录全部提示和输出？它们可能包含凭据、代码和用户数据；要按用途决定保存内容与期限，并能重建必要证据。当前已有历史和终端显示，持久 JSONL 轨迹属于 M5a；用量不可得时标为缺失，不当作零。

### Q27. 如何降低 Agent 延迟和费用？

**参考回答〔方案题〕：**先分解一次任务的模型等待、生成、工具执行和协调耗时，记录输入/输出 token 与实际调用次数。再考虑减少无效往返、压缩低价值工具输出、选择相关上下文、对独立只读任务并行，以及经过评测的模型路由和缓存。流式主要改善可感知等待，不自动减少完整任务时间或 token。优化要同时观察任务成功率、尾延迟和总成本，而不是只看单次调用便宜。

**追问：**为什么不把所有工具结果缓存？结果可能依赖文件版本、用户权限、环境与时间；写操作结果也不能当只读数据重放。当前没有完整成本报表或缓存收益数据，只能说明测量与验证方案。

### Q28. ReAct、plan-execute、Reflection 各适合什么任务？

**参考回答〔现有循环；第二模式待实现〕：**ReAct 根据观察逐步行动，适合反馈会改变下一步的任务；plan-execute 先形成计划，再按执行证据推进或修订，适合存在可分解步骤的任务，但计划也可能过时。Reflection 用反馈检查和改进结果，有外部测试时更容易判断是否有帮助；只让模型自评可能重复同一错误。我的计划是在相同多步靶子与预算下比较，再从两个实现提炼模式接口。

**追问：**计划一旦确认是否可以随意新增操作？计划确认的范围需要明确，重规划不自动扩大工具权限。当前未实现 plan-execute，不会把后续对照实验写成已取得的收益。

## 七、多 Agent、协议与系统设计

### Q29. 多 Agent 为什么可能更好，也可能更差？

**参考回答〔M8a 计划〕：**适合拆成相对独立任务时，它能并行调查并隔离上下文；但会增加请求、重复工作、沟通损耗和结果冲突。我的第一步是主 Agent 加两个只读调查子任务，各自独立历史，只交接带来源的结果；主 Agent 核实结论再修改。比较时用同一任务和明确资源预算，不把多花调用得到的结果直接称为架构优势。

**追问：**两个子 Agent 都说自己对怎么办？回到代码或测试核实；多数票不自动等于事实。还要设计超时、取消传播和部分结果处理。需要并发写文件时再考虑工作区隔离与合并冲突；当前并未实现这些协作能力。

### Q30. Function Calling、MCP、A2A 有什么区别？

**参考回答〔M8b/M8c 计划〕：**Function Calling 描述模型怎样提出结构化调用；MCP 为应用连接外部工具、资源和提示模板等能力提供协议；A2A 面向 Agent 之间的能力发现、消息、任务状态与产物交互。它们处在不同层，可以组合：应用通过 MCP 获取工具，把定义转换给模型；模型选择后应用调用服务。另一项工作也可以委派给支持 A2A 的 Agent，再跟踪任务与结果。

**追问：**把 Agent 包成 MCP 工具就不算 Agent 通信了吗？实现上当然能调用另一个 Agent，但暴露工具不自动实现 A2A 的任务语义。MCP 不替应用生成可信权限，A2A 不替你完成协作策略；具体字段、SDK 和兼容性实施时按官方版本核实。当前项目两个协议均未接入。

### Q31. 如果把这个 CLI 改成多人使用的编程 Agent 服务，你怎么设计？

**参考回答〔生产扩展题〕：**先问清任务类型、并发量、信任范围、延迟目标和部署限制，再画最小链路：请求鉴权 → 创建运行记录并入队 → Worker 在隔离工作区执行 → 持久化状态和结果 → 向前端推送事件。模型选择行动，执行端校验权限。每个运行绑定用户、项目与配置，历史和产物按作用域存储；取消要传到实际执行器，重连读取状态而不是重新执行命令。

**追问与取舍：**Worker 崩溃在“已写文件、结果未落盘”之间，不能直接全量重跑；记录 unknown 并核实执行状态，适合的操作才用幂等键。资源控制分别考虑并发、请求速率、时长和 token；凭据由服务端注入，不写进历史；生产隔离、存储与队列需按需求验证。当前 CLI 没有这些能力，这是一份设计回答，不是已部署架构。

### Q32. 面试官问“哪些是你做的，效果怎么样”，怎么回答？

**参考回答：**说明自己的实际分工：核心代码手写，Codex 协助规格、接口、测试和评审；挑一个自己能现场解释的模块展开。效果讲能核查的任务结果、修改范围和失败边界。比如历史记录中的独立靶子从红变绿、固定测试未改，以及取消配对的回归场景。用量、成功率、线上用户数和节省时间没有测过，就不编数字；未来阶段用“计划实现”明确区分。

**可用的项目描述模板：**“用 Python 实现基于原生工具调用的编程 Agent，完成 Bash 读改测闭环；实现参数校验、工具结果与调用 ID 配对、超时/取消清理和有界输出读取，通过 FakeLLM 与独立靶子验证关键边界。”使用前确认每项仍与自己的代码、贡献和验收一致。不要追加尚未完成的 RAG、多 Agent、生产部署或流式闭环。
